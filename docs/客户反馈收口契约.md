# 客户反馈收口契约 · v1

> 将来要做的服务器，照这份写就行。**这份文件描述的是数据长什么样，不是它怎么送过来。**

## 为什么先定契约、后建服务器

备案和服务器周期长，产品上线不能等它。所以现在把**数据格式**定死，把**运输方式**做成可换的：

| | 运输方式 | 客户要做什么 |
|---|---|---|
| 现在（没有服务器） | 编码进客户手机的剪贴板，顺手拉起微信 | 点一下「复制并打开微信」，粘贴发送 |
| 将来（有了服务器） | 客户页直接 `POST` 到收口地址 | 点一下「发送给纫荃」，完 |

**两条路送的是同一个载荷。** 所以：

- 服务器上线那天，客户页不用改代码，只要在「客户页」页签里填上地址、重新导出一次。
- 上线之前用离线路收回来的反馈，和上线之后收到的，格式完全一样，能混在一起算。

## 载荷

`POST <收口地址>`，`Content-Type: application/json`：

```json
{
  "v": 1,
  "cat": "FW",
  "code": "FW-401B",
  "ref": "2503-0007",
  "source": "customer",
  "date": "2026-09-18",
  "values": { "warmth": "cold", "stayed": "on", "damp": "dry", "wrap": "good" },
  "nights": "1",
  "overall": "misfit",
  "words": "",
  "releasable": false,
  "advice": "眠足 厚款"
}
```

| 字段 | 含义 |
|---|---|
| `v` | 载荷版本。字段集变了就 +1，旧反馈还认得出来 |
| `cat` | 品类码 |
| `code` | 型号编码。**来自链接里的 `?m=`，不是客户自己选的** |
| `ref` | 批次／订单号。来自链接里的 `&r=`，批次层还没建，位置先留着 |
| `source` | 固定 `"customer"` |
| `date` | 客户答题当天 |
| `values` | 品类字段的答案，键就是字段契约里的 `key`。**加新品类不改这个结构** |
| `nights` | 用了多久（客户页独有） |
| `overall` | 总评：`fit` / `misfit` / `issue` |
| `words` | 客户原话，可空 |
| `releasable` | 客户是否同意匿名引用 |
| `advice` | 页面当时给出的建议。用来回头看推荐准不准、客户听不听 |

**这个形状就是 `records` 的一条。** 服务器那头要做的只是把收到的 JSON 原样写进 `records` 集合，不需要转换。

## 服务器最少要做什么

1. 收 `POST`，解 JSON，校验 `v` 不高于自己认得的版本。
2. 校验 `code` 在产品库里存在——不存在就拒收并记下来（多半是链接被改过）。
3. 写进 `records`。
4. 返回 2xx。**非 2xx 客户页会提示重试，并给出「复制内容手动发给我们」的兜底**，所以失败不会把客户卡死。

不需要登录，不需要会话。**但要防重复提交**（同一 `code` + `date` + `words` 视为同一条）和刷量。

## 离线那条路的编码

客户复制的那段文字，末尾带一行：

```
#RQ1:<base64>
```

`1` 是 `v`，`base64` 是上面那个 JSON 的 UTF-8 base64。测试台「记感受」页签的「粘贴客户反馈」整段粘进去就能还原——**和服务器收到的是同一份东西**。

## 客户链接的格式

```
<客户页地址>?m=<型号编码>&r=<批次或订单号>
```

- `?m=` 必须带。不带的话页面会退回让客户自己从列表里挑，**而他大概率会挑错**——挑错的记录比没有记录更糟，它会挂到错的型号上污染那一款的数字，而且看不出来。
- `&r=` 可选，批次层建好之前先留着。**现在不带，以后补不回来。**

每个型号的链接后缀，在测试台「客户页」页签里列着。
